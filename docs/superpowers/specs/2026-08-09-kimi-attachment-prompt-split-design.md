# Kimi 附件 + Prompt 分流设计

Date: 2026-08-09

## 目标

把页面总结流程改成两条通道：

- 网站标题 + 页面正文作为附件
- 剩余总结提示词作为普通文本 prompt

这样比“把一段长文本粘贴进去，等 Kimi 自己判断是否转成附件”更稳定，也更容易排查。

## 为什么这样做

Kimi 的现有界面看起来支持文件上传，因此把 `标题 + 正文` 做成临时文件再注入，是一条更明确、可验证的路径。

我们不把“粘贴长文本会变成附件”当作主路径，因为这类行为可能受长度、编辑器状态、浏览器版本和页面前端实现影响。

## 用户流程

1. 用户右键页面选择 `总结页面`。
2. 扩展提炼页面正文，生成 Markdown。
3. 扩展生成两部分内容：
   - 附件内容：`页面标题 + 页面正文`
   - Prompt 内容：总结指令、输出格式要求、额外约束
4. 用户进入侧栏确认页。
5. 扩展创建一个临时文本文件，供 Kimi 作为附件使用。
6. 扩展把 Prompt 输入 Kimi 文本框。
7. 用户手动发送，或在确认后自动发送文本 prompt。

## 内容分流规则

### 附件

附件只承载事实材料，不承载任务要求。

建议内容：

- 页面标题
- 原始 URL
- 提炼出的正文 Markdown

推荐文件名：

- `page-title.md`
- 或 `page-title.txt`

### 文本 prompt

Prompt 只承载任务指令，不重复正文。

示例：

```text
请基于我上传的页面正文，总结主要内容、关键观点和可继续追问的问题。
输出请使用中文，并按“摘要 / 要点 / 追问”结构组织。
```

## 技术实现

### 1. 页面提炼

保持现有 `source-extractor` 逻辑：

- 优先提炼正文 Markdown
- 失败时走 URL 方案
- Reddit 等特殊站点继续使用现有专用提炼逻辑

### 2. 临时文件生成

把附件内容拼成一个临时 `.md` 或 `.txt` 文件。

要求：

- 文件内容必须包含页面标题
- 文件内容必须包含正文
- 文件名中尽量保留标题语义
- 不持久化到用户目录，使用临时 Blob / File 对象即可

### 3. 附件注入

Kimi 侧栏页面如果能拿到文件上传入口，就优先走文件上传控件。

优先路径：

- 找到文件上传按钮或拖拽区
- 通过 `File` / `DataTransfer` 模拟用户上传

如果上传入口在当前 DOM 不可稳定定位，则降级为：

- 只填 Prompt
- 提示用户手动上传附件

### 4. Prompt 输入

Prompt 继续通过现有 Kimi 输入框注入。

但要注意：

- 附件和 Prompt 是两条独立路径
- Prompt 里不要重复正文
- 自动发送时只发送文本 prompt，不把正文再次塞进输入框

## 状态机

建议拆成三个状态：

- `review`: 展示提炼结果、附件内容、待发送 prompt
- `attach`: 上传临时文件到 Kimi
- `compose`: 填写文本 prompt

成功标准：

- 附件已进入 Kimi 上传区
- Prompt 已进入 Kimi 输入框
- 手动或自动发送后，Kimi 接收到两者但不重复正文

## 风险

- Kimi 的上传控件可能改版
- 文件注入可能被前端事件链拦截
- 某些站点正文过长，临时文件可能需要截断
- Kimi 对“同一内容既作为附件又作为文本”可能会造成重复理解

## 退路

如果附件路径不可稳定实现，保留两种退路：

1. 只填 Prompt，不附加附件
2. 提供“复制正文 / 下载附件”按钮，让用户手动上传

## 验收标准

- 页面总结后，Kimi 中只出现一份正文附件
- Prompt 区只出现总结指令，不重复正文
- 关闭确认步骤后，附件和 Prompt 仍能正确分流
- 日志能明确区分：
  - 附件是否生成
  - 附件是否注入成功
  - Prompt 是否输入成功

## 待确认问题

- 附件只做 `.md`，还是 `.md` + `.txt` 双格式兜底
- 自动发送是否只针对文本 prompt，还是附件注入成功后一起自动触发
- 附件失败时是否提示用户手动上传，还是直接降级为纯文本模式
